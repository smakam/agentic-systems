# Evaluation — Instructor demo and learner exercise

Use this document as the starting point. The instructor walkthrough uses recorded results and one live code-evaluator test; learners complete two supplied-answer activities. Neither requires new model calls.

- [Instructor demo](#instructor-demo): orientation, three evaluation examples, then one native evaluator sample test.
- [Learner exercise](#learner-exercise): grade and upload five human reviews, then create an evaluator and grade three supplied structured answers.
- [Worked answers](solutions/answers.md): open after completing the learner exercise.

## Instructor demo

### Workspace for this activity

Use [local Langfuse](http://localhost:3000), project **marketplace-support**, and the supplied saved answers. No marketplace UI or business database is required for this activity. Run the documented import commands from the application repository root; keep the configured Langfuse worker and dispatcher running.

Start with recorded results, then run one native code-evaluator sample test in the UI. Do not run scripts or make model calls during the demonstration. The scripts remain available separately for preparation and learner uploads.

### Langfuse navigation

| Section | What to show |
| --- | --- |
| Datasets | Test questions, golden references and metadata |
| Experiments | Recorded model answers and their evaluation scores |
| Evaluators | Automated grading code and the rule selecting answers to score |
| Human Annotation | Human review inside Langfuse; available, but not used in this demo |
| Scores | User feedback, human grades and automated grades; each row is one score |

A dataset is not a set of model answers by itself. Its expected output is the golden reference. The experiment's OUTPUT is the candidate answer; the evaluator produces scores and reasons.

### Part A — Nano answers graded externally by Claude

**Objective:** show how an external Claude judge graded saved Nano answers, and how Langfuse displays the imported answers, scores and reasons. Follow **Datasets → Experiments → one answer and its grade**.

#### 1. Show the five golden cases

In Langfuse, select **Datasets** in the left sidebar, then open the [chapter14-claude-v1 dataset](http://localhost:3000/project/marketplace-support/datasets/cmv6hmtqx0017r007w81poch4/items).

Confirm five items. Pick the product-and-quantity question for order-1. Show its input and expected facts: two Canvas Weekenders from Cedar and two Desk Lamps from Northstar. Explain that these references were established independently of the candidate answer.

#### 2. Show the recorded experiment and model identities

In Langfuse, select **Experiments** in the left sidebar. In the **Dataset** filter, select `chapter14-claude-v1`, then click the experiment name [chapter14-claude-five-live](http://localhost:3000/project/marketplace-support/experiments/results?baseline=fd1dd08edbe5c45c).

For optional model details, stay in **Experiments** with the same dataset filter and select [chapter14-nano-claude-model-details](http://localhost:3000/project/marketplace-support/experiments/results?baseline=617004fb6c879e31).

Confirm five items. The main run identifies its grading source and reuse of supplied answers. If explaining exact model identities, select the model-details experiment described above, then use **Show details / Metadata** on its results page: **GPT-5 nano** is the answer model, and **Claude Opus 5.5** is the configured judge model. That labelled alternative records model versions, judge identity basis, grading method and rubric.

The saved judge response records the gateway alias; the Claude provider name is the configured LiteLLM route, labelled accordingly. Our script ran Claude outside Langfuse and imported its grades. No new answers or judgments were generated by this model-labelled import. The historical runs remain separate.

#### 3. Compare question, gold, candidate answer and Claude judgment

Read one row across: **Input → Expected Output → OUTPUT → claude_correctness**. OUTPUT is Nano's saved answer, not an answer generated by Claude.

Use three examples:

| Question | Score | Meaning |
| --- | ---: | --- |
| Products and quantities in order-1 | 2 | Correct: required products, quantities and sellers match |
| Has the payment gone through for order-1? | 1 | Partial: buyer payment is described, but seller payout is not distinguished |
| Did the payout incident affect every seller? | 0 | Incorrect: the answer asks an unrelated clarification and misses incident scope |

On the **experiment results page**, click the answer cell for one case. In the detail panel, select **evaluator** in the middle trace tree, then scroll the right panel to **Output**. Read `claude_correctness`, its value and comment/reason. The question, candidate answer and gold appear within the evaluator input; the grading result is its output. Select the answer/task span to inspect the original agent answer separately. Compare that explanation with the golden requirements. The full five scores are **2, 1, 1, 1, 0**. An error count of zero means no experiment-task execution errors, not zero incorrect answers. The displayed average **1.00** is an average on the 0–2 scale, not a percentage or a count of correct answers.

#### 4. Explain where grading happened

On the **experiment results page**, use **Show details** to inspect the description. It identifies external grading. In the selected answer's **score details**, the score source is **API**: our script submitted it. Source API alone does not identify the grader; the experiment metadata and saved judge results establish Claude's role.

The imported task's zero cost describes replay/publication, not the original answer generation or Claude judging. The original five judge calls had a gateway cost estimate of USD 0.192392. No live call is needed for this demonstration.

In its detail panel, select the **chapter14-structured-answer** span in the middle tree; click **+2 / Show all 4 scores** under that span to reveal all checks. ### Part C — Core 18: fixtures, human evaluation and judge comparison

Human correctness is **0**, provisional judge correctness is **0**, and judge–human agreement is **true**. Both marked the answer wrong because it permitted release after only 23 hours. ### Part A — Human evaluation of five answers

**Objective:** assign a human score and reason to each supplied answer, upload all five reviews, and verify them in a named Langfuse experiment.

#### 1. Open the worksheet in this exercise folder

In your local repository, use the editor's file explorer to open [human-worksheet.json](human-worksheet.json) from `course/exercises/evaluation/`. It contains five questions, golden references and actual saved Nano answers. Fill in the score and reason for each answer in this file.

After completing the exercise, use your editor to read the worked answers at [solutions/answers.md](solutions/answers.md) inside this exercise folder.

#### 2. Grade each model answer

In `course/exercises/evaluation/human-worksheet.json`, update each object in the `cases` array: replace `score: null` with **0 incorrect**, **1 partially correct**, or **2 correct**, and fill `reason` with a short fact-based explanation. Compare `model_answers` with `golden_facts`; leave `questions`, `golden_facts`, `model_answers` and `case_id` unchanged. Repeat for all five cases. Equivalent wording is acceptable. Use **2** when all required facts are correct and supported, **1** when the answer is useful but incomplete without a wrong central conclusion, and **0** when the central conclusion is wrong, unsupported, or does not answer the question. Judge citation/evidence requirements against the supplied reference; do not award full credit merely for fluent wording.

For example, a completed case contains these two fields (choose your own grade and reason):

```json
"score": 2,
"reason": "The answer includes all required facts and matches the golden reference."
```

#### 3. Validate the completed JSON

```sh
docker compose -p marketplace-lab -f app/compose.yaml --profile evaluation \
  run --rm --no-deps \
  -v "$PWD/course/exercises/evaluation:/exercise:ro" \
  eval-runner python /exercise/scripts/publish_human_reviews.py \
  /exercise/human-worksheet.json
```

**Expected:** five validated reviews and zero model calls. Missing scores, invalid values, blank reasons or changed question/gold/answer fields are rejected.

#### 4. Upload your human grades to Langfuse

```sh
docker compose -p marketplace-lab -f app/compose.yaml --profile evaluation \
  run --rm --no-deps \
  -v "$PWD/course/exercises/evaluation:/exercise:ro" \
  eval-runner python /exercise/scripts/publish_human_reviews.py \
  /exercise/human-worksheet.json \
  --publish --run-name chapter14-my-human-review
```

**Expected:** the script prints an experiment URL. Follow it to the **Langfuse experiment results page**. To navigate manually, select **Experiments** in the left sidebar, set the **Dataset** filter to `chapter14-human-v1`, then select `chapter14-my-human-review` (or the run name used in your command). Click an answer cell, select **evaluator** in the middle trace tree of the detail panel, then scroll the right panel to **Output**. `human_correctness` is your score and its comment is your reason. The source is **API** because the script uploaded the grades; the metadata records human grading. An error count of zero means the publication task had no execution error, not that all answers are correct. Langfuse displays your imported human grades; it does not grade them again. Use a new run name for another submission.

### Part B — Native evaluation of three structured answers

**Objective:** create a native code evaluator in your own Langfuse project, import three supplied JSON answers into a named experiment, and inspect their native scores. No new agent/model answers are generated.

#### 1. Create the evaluator in your own Langfuse project

The instructor's evaluator is local to the instructor's project. In your project, complete the following setup before importing the three answers. The human-grading upload in Part A does not require this evaluator.

##### Enable the code-evaluation runtime

From the repository root, with the normal Course Setup services already running:

```sh
docker compose -p marketplace-lab \
  -f app/compose.yaml \
  -f course/exercises/evaluation/setup/compose.code-eval.yaml \
  up -d --no-deps langfuse-web langfuse-worker

docker compose -p marketplace-lab \
  -f app/compose.yaml \
  -f course/exercises/evaluation/setup/compose.code-eval.yaml \
  ps langfuse-web langfuse-worker
```

Confirm both services are running. Include any additional Compose overlays used by your local setup as well. The supplied overlay enables the TypeScript dispatcher and worker queue; include it whenever you recreate these two services for this activity. It retains existing data and does not reset the marketplace. This local dispatcher runs trusted supplied TypeScript in the worker process; use the reviewed course evaluator, not untrusted code. Refresh Langfuse after restarting.

##### Add the TypeScript evaluator

1. In your browser, navigate to [local Langfuse](http://localhost:3000) and select your project (`marketplace-support` in the standard local setup). Import credentials must belong to that same project.
2. Open **Evaluators** in the left sidebar, then **New evaluator**.
3. Choose **Code evaluator** in the gallery and select **TypeScript** as the language. Do not choose an LLM-as-a-judge evaluator for this task.
4. In your local repository's editor, open [structured-evaluator.ts](structured-evaluator.ts) from `course/exercises/evaluation/`, copy its complete contents and replace the sample code in the editor. This is the grading code. `structured-three.json` is input data and must not be pasted as code.
5. Set the name to **Chapter14 structured order comparison**. Suggested description: “Compare shipment status and quantity with independent expected fields.” Save the evaluator using the page's save control. Exact control labels can vary with Langfuse version.
6. Do not expect sample observations yet in a fresh project. First save the evaluator and configure its rule below; import the supplied answers in step 3, then test a sample in step 4.

The code reads the actual answer from `ctx.observation.output`. It reads the reference from `ctx.experiment.itemExpectedOutput`, falling back to `ctx.observation.metadata.expected_output`. The importer supplies those references. There is no judge-model configuration, provider API key, or separate prompt-variable mapping for this code evaluator.

##### Attach and enable an observation rule

1. On the saved **evaluator configuration page**, select **Rules** near the top and create an observation rule, or attach this evaluator to an existing suitable rule. If your project already has the course rule, reuse it instead of creating a duplicate.
2. Set the observation **Name equals `chapter14-structured-answer`**. This is the answer observation emitted by the supplied importer, not the experiment's overall root span.
3. Attach **Chapter14 structured order comparison**, set sampling to **100%**, and save/enable the rule for new matching observations. In a shared project, also restrict it to your lab dataset/experiment using available filters, or use an isolated project.
4. Confirm the evaluator has one appropriate enabled rule before importing. The filter selects what gets graded; dataset `judge_model` metadata only describes provenance and does not switch on grading.

**Expected setup result:** your project contains the saved TypeScript evaluator and an enabled matching rule. No sample test or new experiment has run yet. The upcoming import creates the observations that the rule will grade.

#### 2. Inspect the supplied JSON

In your local repository's editor, open [structured-three.json](structured-three.json) from `course/exercises/evaluation/`. Each item has a question, expected shipment status and quantity, and an actual recorded GPT-5.4 answer. Do not generate new model answers.

#### 3. Import the three outputs

```sh
docker compose -p marketplace-lab -f app/compose.yaml --profile evaluation \
  run --rm --no-deps \
  -v "$PWD/course/exercises/evaluation:/exercise:ro" \
  eval-runner python /exercise/scripts/upload_structured_answers.py \
  --fixture structured-three.json --publish \
  --run-name chapter14-my-structured-review
```

**Expected:** three imported items, zero model calls and an experiment URL. The script creates the dataset `chapter14-learner-structured-three-v1` and the experiment `chapter14-my-structured-review` (the run name in the command). It imports answers, not grades.

#### 4. Test the native evaluator

In Langfuse, select **Evaluators** in the left sidebar, then select **Chapter14 structured order comparison**. On the right, use **Test with sample observations**. Select the radio button for one of your imported `chapter14-structured-answer` rows, then click **Run test on this sample**. Inspect the returned checks. This reruns code grading of a saved answer; it makes no new agent answer and does not create an experiment. Inspect the TypeScript source and confirm the rule targets `chapter14-structured-answer` at 100% sampling. Reuse the existing rule. If using a shared project, restrict it to your dataset/experiment where appropriate.

The import creates a named experiment and links each saved answer to a dataset item. The enabled observation rule triggers grading automatically; you do not need the UI **Run experiment** button for this supplied-answer workflow. The Langfuse worker executes the comparison asynchronously. If the rule was created after import, include past matching observations. Upload completion alone does not mean grading finished.

#### 5. Inspect the experiment results

Follow the URL printed by the import command to the **Langfuse experiment results page**. To navigate manually, select **Experiments** in the left sidebar, set the **Dataset** filter to `chapter14-learner-structured-three-v1`, then select `chapter14-my-structured-review` (or the run name used in your command). Compare question, golden fields, actual JSON and scores on that page. Record `schema_valid`, `status_matches`, `quantity_matches`, and `structured_grade`. Confirm source **EVAL** for native scoring. The three supplied outputs match their references, so expect three `correct` grades and true schema/status/quantity checks. The overall grade is categorical; it does not use the human 0–2 scale. Explain what each check proves; these field checks do not establish citation grounding or full semantic correctness.

#### If the sample test cannot run

If it reports **code eval dispatcher is not configured**, repeat the runtime setup in Part B step 1 for both Langfuse web and worker, preserving any additional local Compose overlays. Refresh and repeat the sample test. A passing sample test confirms that one code execution works; separately check the scores on all three experiment items. If scores remain absent, check the enabled rule, matching observation name, 100% sampling and worker queue before importing another run.
